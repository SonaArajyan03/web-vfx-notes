Keep effect data as plain JSON in your repo

The format your effects are stored in decides whether they can be reviewed, and almost nobody picks it deliberately.

Most visual authoring tools save to a proprietary binary blob, or worse, to a cloud project you access through a web app. It feels irrelevant while you are authoring. It becomes very relevant the first time someone asks “what changed in this effect?” and the honest answer is “nobody can tell”.

What plain files give you

  • A reviewable diff. A pull request that says lifetime: 0.6 -> 1.4 is a conversation. A pull request that says Binary file changed is a rubber stamp.
  • Real version history. You can bisect a visual regression the same way you bisect any other one. With a binary blob you can only restore wholesale.
  • Automation without an API. If effects are JSON, a script can validate them, batch-edit them, lint them for expensive settings, or generate variants. None of that needs the tool's cooperation.
  • No hostage situation. Your effects live in your repository. If the tool disappears, changes pricing, or moves to a cloud-only model, you still have the data and the schema.

The agent angle, which is new

This one changed my mind about how much the format matters. Plain JSON with a documented schema means a coding agent can create and modify effects directly — no GUI, no screen-reading, no browser automation. It reads the schema, writes the file, runs a validator, exports. That loop works headlessly and it is checkable at every step.

You cannot do that with a binary format at all, and you can only barely do it with a web app, via exactly the kind of brittle UI automation everyone regrets. The choice of storage format quietly decides whether half your VFX work can be delegated.

The honest cost

JSON project files get verbose, and a large effect graph is not pleasant to read raw. That is fine — you are not meant to read it raw, you are meant to be able to. And a noisy diff still beats no diff.

The pattern worth copying is create, edit, validate, export as four separate steps with a non-zero exit on failure — this CLI reference is a good concrete example of that loop, including the read-only validate pass, which is the step people leave out.
