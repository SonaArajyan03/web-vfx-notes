Notes on web game VFX
Particle effects, frame budgets, and authoring workflow for HTML5 games.

Say which parts did not survive the export

Any tool that targets two renderers will eventually hit something one of them cannot do. What matters is whether it tells you.

I lost most of an afternoon to this once. An effect used a per-particle velocity module, looked right in the editor, and rendered subtly wrong in the 2D backend — not broken, just flat. Nothing errored. The module was silently unsupported on that path, so it was skipped, and the result was plausible enough that I assumed I had mis-tuned it and kept adjusting the wrong numbers.

Silent degradation is the worst failure mode

Loud failure is fine: you see it, you fix it. Correct output is fine. The expensive case is output that is almost right, because you spend your time debugging your own judgment instead of the tool.

So the property I now look for is not "supports everything on every backend" — nobody can promise that — but a machine-readable report of what was supported, partially supported, or dropped, produced at export time. Three things follow from that:

  • You can fail a build when an effect uses something its target backend does not implement. That turns a visual bug into a CI error.
  • You can diff the report across versions and notice the day an upgrade quietly changed support.
  • An agent can read it, which means the fix loop can be automated instead of requiring someone to eyeball two renders side by side.

The workaround worth knowing

When a module genuinely is not available on your target, the fix is usually to express the same motion with a primitive that is. Buoyancy via a negative gravity force instead of a velocity-over-lifetime curve, for instance — less expressive, identical on screen, and portable. You only find these substitutions if the tool told you what was dropped.

The general version

This is really a documentation-honesty test. A tool that publishes its per-backend support matrix is telling you it expects you to hit the edges. One that markets seamless portability without a compatibility report has moved the discovery of those edges from build time to ship time.

The runtime reference covers the module and backend matrix, which is the document you want open while authoring anything cross-renderer.
