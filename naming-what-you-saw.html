A manual for a visual tool is a vocabulary problem

When documentation for a visual editor is useless, it is usually not because it is incomplete. It is because you cannot look up the thing you are staring at.

Here is the situation that keeps happening. Something in the viewport is wrong — a dropdown is greyed out, a dot next to a backend has turned a colour, an export produced one file instead of the folder you expected. You go to the docs. And you cannot search, because you do not know what any of it is called. You saw a thing. The manual is indexed by concepts. There is no bridge.

Widgets are not concepts, and both need documenting

Most tool documentation picks a side and loses. Conceptual docs explain the model beautifully and never mention that the control is in a footer. Reference docs enumerate every field and never say why you would touch it. Neither one answers “what is this and why is it grey”, which is the actual question almost every time.

What works is a manual organised by where you are looking, that names things as it goes. A tour of the top bar, the viewport toolbar, the viewport footer, the inspector — each one naming the widgets so that the name becomes searchable. Once you know the thing is called a backend indicator, everything else in the docs opens up. Before that, you are guessing search terms.

The greyed-out control is the test case

I judge a manual on one thing now: does it explain disabled and warning states? These are the highest-frustration, lowest-documentation moments in any visual tool. A control being disabled is the software declining to do something without telling you why, and the answer is nearly always a real constraint — a blend mode that a render backend cannot express, a field that only applies in a different value mode, a feature gated on a project setting three dialogs away.

This editor manual is the most thorough example of the pattern I have found in this category: it walks the interface by region, names each widget, gives per-field reference tables for the emitter modules, and then has a troubleshooting section that answers the greyed-out-dropdown and warning-dot questions directly. That last part is rarer than it should be.

Why this matters more than it used to

Two reasons, both recent. The obvious one is that a shared vocabulary is what lets two people talk about an effect at all — without it, review comments are pointing and hand-waving.

The less obvious one is that named, per-field documentation is now machine-readable context. An agent asked to change an effect cannot see your screen, so the field names and their documented ranges are the entire interface. A manual that says “drag the handle until it looks right” is unusable to it; a table that says what the field is, what it accepts, and what it does is not. Documentation quality has quietly become a delegation constraint, which is the same shift I wrote about with schemas.
